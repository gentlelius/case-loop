# 用例设计与编写指引

生成和修改用例正文前阅读。按本次需求选择适用检查点，优先保证规则准确、步骤可执行、预期可判定，不以用例数量或分类齐全作为完成标准。

## 先确定规则依据

- 从需求、接口契约、设计稿、相关代码和已确认的历史用例中提取条件、操作、结果及约束。每个场景应能对应具体规则或明确的待验证风险。
- 需求与代码、历史用例不一致时，记录冲突及影响范围，按 questions.md 处理；不要把当前实现直接当作正确预期。
- 不自行补全金额限制、长度上限、状态流转、错误码、精确文案或性能阈值。已知约束可生成具体示例数据，未知规则标待补充。
- 区分已确认的验收规则与建议补充的风险场景。后者缺乏预期依据时，在适用的 note 标明「待补充：」及需要确认的规则，不写成已确认结论。
- 无需新增来源字段或单独产出需求矩阵；存在歧义、冲突时，在 note 简要说明依据。公共缺口遵循 schema.md，在最小公共祖先记录一次。

## 按场景选择检查点

界面、功能、接口是设计维度，不是必填字段。沿用现有模块或业务场景分组，不强制创建三类 group，也不增加测试类型字段。

| 维度 | 适用检查点 | 预期应明确 |
| --- | --- | --- |
| 界面 | 展示条件、默认值、必填与校验、按钮状态、加载/空/失败状态、跳转与回显 | 哪个控件在什么条件下显示什么、能否操作、操作后停留或跳转位置、数据如何回显 |
| 功能 | 主流程、业务分支、输入边界、状态流转、角色与数据权限、重复操作、失败恢复 | 初始与最终业务状态、产生或更新的记录、关键失败时不得发生的变化 |
| 接口 | 方法与路径、鉴权、参数必填/类型/范围、响应结构、业务错误、数据副作用；适用时检查幂等、分页和并发 | HTTP 状态与业务码、关键响应字段的值或关系、持久化变化、重复请求的处理结果；仅断言有依据的内容 |

- 用户明确限定验证范围时遵循该范围。只有界面资料时，不猜测接口路径、请求结构或服务端错误码。
- 不重复生成仅入口不同、没有新增验证价值的用例。界面禁用非法操作与接口拒绝绕过界面的非法请求，分别验证前后端约束，有独立价值。
- 界面校验只证明界面行为；服务端拒绝、数据未写入等结论需有相应接口响应、查询或其他可观察证据，并写清检查方式。
- 不给所有功能无差别添加性能、兼容性或并发用例；依据用户范围、已知要求和具体风险选择。

## 选择场景设计方法

- **等价类**：按会触发不同规则的有效和无效输入分组，选择有代表性的数据；不要堆叠结果相同的随机输入。
- **边界值**：覆盖已知边界及相邻有效/无效值。明确字符或字节单位、数字精度、日期时区和端点是否包含；只处理会影响本次结果的约束。上限未知时使用「超过上限 1 个字符」等关系表达，并标明规则待补充。
- **决策表**：多个条件共同决定结果时，覆盖不同结果及关键条件组合；避免无依据地穷举所有组合。
- **状态迁移**：覆盖允许和禁止的状态变化，以及重复操作；写明初始状态和触发动作。
- **风险补充**：涉及支付、库存或其他关键写入时，按实际机制考虑重复提交、并发、超时重试和一致性。机制或结果不明确时记录待补充，不默认具有幂等或自动回滚能力。

## 编写可执行、可判定的用例

- 一条用例验证一个明确行为或规则分支，可包含支撑同一行为的多个断言。结果独立、前提不同的分支拆开写。
- 标题采用「条件 + 操作 + 结果」，避免「验证某某功能正常」。
- 前置条件明确初始业务状态、角色和必要数据；公共条件放在 root/group，case 仅补特殊条件。真实数据没有依据时写数据要求，不伪造可用账号或订单。
- 步骤写明具体操作和输入，一步一条；普通输入直接写进步骤，复杂数据块才使用 inputData。接口场景使用已知的方法、路径及必要请求内容，敏感凭据用引用或占位符。
- 预期写可观察、可判定的状态、字段或关系，禁止只写「正常」「成功」「符合预期」。多项断言在 expectedResult 字符串中分行或编号，与步骤对应，不改变字段类型。
- 关键失败场景同时检查错误反馈及相关业务数据的一致性；需要验证数据未变化时，写明操作前后如何检查。没有观测手段时记录缺口，不把未检查的副作用当作已验证。
- 精确文案、错误码和时间阈值仅在依据明确时断言。文案未约定但提示语义已确定时，验证语义即可，不为非关键字面差异追问。

### 示例：数量上限

假设已确认：数量只能填写 1～99 的整数，非法数量不得创建业务记录；界面有提交操作及可查询新增记录的入口。

- **标题**：数量填写 100 时阻止提交且不创建记录。
- **前置条件**：其他必填字段均合法，记录当前相关业务记录。
- **步骤**：将数量填写为 100；点击提交；通过已知查询入口检查本次操作是否新增记录。
- **预期**：展示数量超出上限的校验信息；没有本次操作产生的新记录。精确文案未约定时不限定字面内容。

同一规则还可选择 1、99 等边界，以及 0、非整数等不同无效类别；按验证目标拆分，不把所有输入塞进一个无法定位失败原因的用例。若仅确认界面规则、没有记录查询依据，则只生成有依据的界面断言，数据副作用验证按缺口处理。

## 写入前内容自检

- 每条用例是否对应明确规则或已标注的待验证风险？是否误把现有实现当作验收依据？
- 前置条件、输入和步骤是否足以执行？预期是否足以判断通过或失败，且具有可用的观察方式？
- 已确认的主流程、规则分支、关键边界和权限限制是否遗漏？无需覆盖本次范围外的所有维度。
- 是否存在仅换标题或输入、没有新增验证价值的重复场景？
- 是否编造未知业务规则、真实数据、接口信息、精确文案或阈值？相关缺口是否已集中记录？
- 修改功能时，是否覆盖变更影响的已有流程，并按 schema.md 保留未涉及节点、处理过时用例？

修正可确定的问题后写入，缺口不阻塞其他用例生成。新增用例仍按 schema.md 保持 draft；内容自检不代表实际执行通过。
