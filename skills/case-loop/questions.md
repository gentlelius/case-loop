# 只问必要缺口

先使用需求、代码和已有用例中的信息。信息足够即可生成，不安排固定的问答轮次，不要求用户填写字段表。

## 需要追问

只有缺失信息会改变测试目标、主成功路径或可观察结果时才问。例如「登录失败要有提示」且没有进一步依据，可集中问：密码错误和账号不存在是否需要区分提示？未确认的文案标待补充，不自行编造。

修改时先确定对应文件及变更行为；文件有歧义才询问。能从变更内容推导出的受影响用例、保留用例和作废用例由 agent 判断。

## 自动处理

- 普通字符串、数字、日期和边界输入：依据已知约束生成具体示例，直接放进步骤。
- 未知边界：写清「超过上限 1 个字符」这样的关系，并将上限规则标为待补充，不虚构数值。
- 优先级：主路径无法使用、严重错误可标 blocker；主要功能及常见异常标 major；次要展示标 minor。用户可修改。
- 公共账号、环境、数据：使用已有信息，在适用的 root/group 维护一次，不逐条追问。真实账号和订单不存在依据时不能伪造为可用数据。
- 非必要备注、独立输入数据：省略。

## 集中补充

同一缺口在最小公共分组记录一次，使用 note 的「待补充：」前缀，说明缺什么及影响范围；仅影响单条用例的缺口留在该用例。生成后集中列出缺口，用户回答一次后更新对应公共节点，相关用例自动引用公共条件。

用户要求直接生成时，生成其余可确定内容，不强制再追问。缺口未解决的用例保持 draft；补齐缺口后移除已解决的待补充说明，不擅自标记为 passed。
