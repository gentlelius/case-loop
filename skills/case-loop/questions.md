# 追问清单

每轮从仍空缺的项里挑 3 到 5 个。问题要指向具体行为，并带上已经知道的名词（页面、接口、角色、旧用例标题）。不要问「还有什么要考虑的吗」。

清单项被用户明确回答，或用户明确说先不做并记入 `note`，才算没有实质缺口。

## 新增

1. 谁在什么入口、什么前提下触发
2. 主成功路径，以及成功时用户或系统能观察到什么
3. 边界和非法输入（空值、重复、越界、并发）
4. 失败或异常时，用户或系统具体看到什么
5. 前置数据、账号、环境
6. 哪些场景是 blocker / major / minor
7. 这次明确不测什么

## 修改

先说明将更新哪个 `.case-loop/<slug>.json`，并点出可能受影响的旧用例标题。除新增清单里仍空缺的项外，再覆盖：

1. 相对上一版，行为变了什么
2. 哪些旧用例要改步骤或预期
3. 哪些旧用例只回归、正文不动
4. 哪些旧用例作废，以及为什么

## 示例

需求只说「登录失败要有提示」时，可以问：

- 密码错误和账号不存在，提示文案是否必须不同？
- 连续失败有没有锁定？锁定后用户看到什么？
- 验证码或第三方登录在这次范围内吗？

旧文件里已有「密码错误仍停留在登录页」时，可以问：

- 这次是改这句预期，还是只补「连续失败锁定」？
- 「记住我」那条用例还成立吗？
